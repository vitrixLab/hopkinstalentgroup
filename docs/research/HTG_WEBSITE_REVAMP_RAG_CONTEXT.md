## 6. Visual engineering doctrine

> Engineer the visual structure first; let beauty emerge from precision, proportion, hierarchy, and restraint.

Apply the Visual Engineering Design Standard:
- Build from intentional geometry, documented grids, alignment, proportion, and consistent spacing.
- Use symmetry when it strengthens the concept; do not force symmetry onto asymmetrical information.
- Establish a clear reading order and one dominant message per composition.
- Use negative space deliberately; reduce redundant decoration and visual noise.
- Typography must establish hierarchy and remain legible at actual display size.
- Color supports semantic hierarchy; it cannot compensate for weak structure.
- Grayscale inspection is a structural diagnostic, not a replacement for contrast/accessibility checks.
- Every revision must name a defect, state the measurable change, and show a rendered before/after comparison.
- Inspect the actual rendered artifact at target sizes. Source code or a prompt alone is not proof of visual improvement.

Anti-patterns: fake UI, fabricated data, arbitrary geometry, superficial A/B variations, repetitive cosmetic revisions, excessive background color, generic luxury effects, ambiguous partner endorsement, and completion claims without rendered evidence.

Do not transfer VitrixLab studio palette values into HTG identity tokens. HTG color values remain subject to HTG's own exploration and approval.

## 7. Six-sheet handoff and approval dependencies

The six-sheet package is governed by Issue #10:

1. **Sheet 01 — Shared Design System:** 01a structural system (grid, composition, breakpoints, spacing, token naming, responsive rules); 01b identity tokens (color roles, typeface, typography, logo geometry, brand tokens).
2. **Sheet 02 — Logo A/B Exploration:** two meaningfully distinct directions, construction, clear space, minimum size, monochrome and small-scale behavior, comparison evidence, name/mark screening. Screening is not legal clearance.
3. **Sheet 03 — Identity Applications:** lockups, monochrome/reversed use, typography, color, spacing, misuse, and relationship-class visual grammar.
4. **Sheet 04 — Homepage:** desktop 1440px and mobile 390px; navigation, hero, capability areas, ecosystem relationships, audience pathways, approved proof, footer, disclosure slots.
5. **Sheet 05 — Responsive and Content States:** mobile/tablet/desktop transformations, navigation, hierarchy, overflow, empty/missing content, interaction states.
6. **Sheet 06 — Implementation Handoff:** component inventory, states, responsive rules, acceptance criteria, per-screen checklist, quality matrix, unresolved register, verified content/relationship controls.

## 9. Comprehension and quality validation

**Stage 1 — plain-text message test:** before Sheet 01b approval. Test whether a reader can explain what HTG is, whom it serves, and what it actually handles from text alone. Record prompt, participant role, observations, ambiguity, and copy changes. Do not invent results.

**Stage 2 — rendered first-screen test:** before Sheet 04 approval. Record viewport, rendered artifact/version, prompt, participant roles, observations, hierarchy failures, and resulting revisions.

Score applicable dimensions 0–4 with evidence. Every critical gate must score at least 3/4; an average cannot offset a failed critical gate. Critical gates include brand fidelity, content/relationship accuracy, responsive behavior, accessibility (WCAG 2.2 AA target for applicable interfaces), and implementation readiness. Retain screenshots, measurements, tests, reviewers, dates, and defect resolution. Reject cosmetic-only changes without a defined defect and measurable rendered improvement.
